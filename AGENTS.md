## Что строим
Прототип CQA (Conversation Quality Analytics) для Freedom Broker за 24 часа: веб-интерфейс на HTML/CSS/JS (без входа в систему), который оценивает работу **оператора** в диалогах по чек-листу, показывает баллы, объяснения и реплики-доказательства, и позволяет подать апелляцию и пересмотреть оценку.

Важное:
- Главная цель: **точность оценок** относительно эталонных (Ground Truth) на 10 новых диалогах на контроле. Затем удобство, функции, честность процесса (система реально анализирует, а не отдаёт заготовленные ответы).
- Языки диалогов: RU, KZ, EN. Роли в диалоге: client, operator, bot, system. Оцениваем только operator; bot и system это контекст.
- Интерфейс должен быть простым HTML/CSS/JS без сборки: его потом могут встроить в Dynamics 365.
- Через ~23 часа откроют контрольные диалоги и **попросят заменить один критерий чек-листа через интерфейс**. Поэтому критерии хранятся в настройках, а не в коде.
- Через 24 часа стоп-код: последний коммит проверяет жюри. Данные и чек-лист можно менять через интерфейс уже после.
- Презентация 5 минут: интерфейс и диалог, оценка с обоснованием и переходом к реплике (пример N/A), апелляция и решение, замена критерия.

5. Не воспроизводим заготовленные ответы. Кеш допустим только с ключом из текста диалога и версии чек-листа.
6. Не добавляй тяжёлые зависимости без согласования с Рамазаном.

## Чек-лист (кратко; полное правило в `src/cqa/checklist.default.json`)
1 Установление контакта (да/нет, вес 10), 2 Выявление потребности (да/нет/N/A, 15), 3 Идентификация (да/нет/N/A, 20),
4 Консультация (шкала 20/15/10/5/0 или N/A, 20), 5 Эмпатия (да/нет, 15), 6 Управление диалогом (шкала 10/7/4/0, 15),
7 Завершение (да/нет/N/A, 5), 8 Грубые ошибки (флаг, без баллов).
Расчёт: «да» даёт полный вес, «нет» ноль, шкала пропорционально весу; N/A выпадает, вес перераспределяется между применимыми; итог округляется до 2 знаков; грубая ошибка отмечается отдельно.
Для каждого критерия нужны: ответ или балл, короткое обоснование, реплика-доказательство (для пропущенного действия место, где его ждали; для N/A объяснение условия).
У критерия есть необязательное поле `rules` (уточнения для модели, попадают в блок «Правила оценки»); редактор чек-листов должен его сохранять.

## Данные
Источник: GET по `group_id` (ссылка в `.env` как `DATA_API_URL`). Запрос делает сервер (из браузера мешает CORS). Формат:
`{"isSuccess": true, "data": {"records": [{"conversation_id", "channel": "agent chat|voice call", "language": "RU|KZ|EN", "transcript": [{"timestamp", "speaker", "text"}], "audio_url"}]}}`.
У чатов время `MM:SS`, у звонков ISO 8601; сохраняем исходные метки. Реплика идентифицируется **индексом в массиве transcript** (`message_index`, с нуля).

## Контракт API (черновик, утверждает Рамазан)
- `GET /api/conversations`: список (id, язык, канал, итог последней оценки)
- `GET /api/conversations/{id}`: транскрипт + аудио
- `GET /api/checklists`, `GET /api/checklists/{id}`, `POST /api/checklists` (сохранить новую версию), `POST /api/checklists/{id}/activate`
- `POST /api/evaluations` `{conversation_id, checklist_id}`: запустить оценку; `GET /api/evaluations/{id}`
  Необязательное `force: true` («Переоценить» на сайте): без кэша и без переиспользования ответов, модель вызывается заново.
- `POST /api/evaluations/batch` `{conversation_ids, checklist_id}`: пакетная оценка
- `POST /api/evaluations/{id}/appeals` `{criterion_id, comment}`; `GET /api/appeals?status=open`
- `POST /api/appeals/{id}/decision` `{decision: "confirm"|"change", new_answer?, reason}`

Результат оценки (JSON):
```
{ "id", "conversation_id", "checklist_id", "checklist_version", "model", "cost_usd", "status",
  "total", "original_total", "section_scores", "gross_error",
  "criteria": [ { "id", "title", "answer", "original_answer", "final_answer", "applicable",
      "weight", "effective_weight", "points", "explanation", "na_reason",
      "evidence": [ { "message_index", "quote" } ], "checked_range": [from_index, to_index],
      "appeal": null | { "comment", "status", "decision", "reason" } } ] }
```
Ссылка в обосновании ведёт на `message_index` (для звонка ещё на время в записи).
Оценка в коде: `from evaluator import evaluate; evaluate(record, checklist, model_name=None)` из `src/cqa/` возвращает JSON выше; без `model_name` берётся первая модель из `EVAL_MODELS` в `.env`, при сбое следующая; поле `model` показывает, кто ответил. Ошибка всех моделей: исключение `EvaluationError`.
Проверка из консоли: `python3 src/cqa/evaluator.py --id p1-ru-001 [--model ...] [--checklist путь]`. Без чек-листа он выбирается по каналу записи (`applies_to`).
Значения `answer`: `"yes"`, `"no"`, `"na"` для да/нет и флага (у флага `"yes"` = нарушение найдено), для шкалы число-ступень (например `15`). Других значений не бывает.
Если все применимые критерии N/A (или их веса 0), `total` и `section_scores` равны `null`, `status` = `"done"`: сервер показывает «итог не рассчитан», не считает такую оценку в средних и даёт поставить итог через апелляцию.
Ошибки: все модели упали или вышел предел `EVAL_TIMEOUT` (по умолчанию 120 с) → исключение `EvaluationError`, сервер сохраняет оценку со `status: "error"` и текстом ошибки и даёт перезапустить; неверный чек-лист → `ChecklistError` с текстом на русском, его показываем пользователю как есть.
